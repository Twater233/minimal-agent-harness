# 架构设计回答

每个模块选一道题。以下以一个持久化、带工具的聊天 Agent 为背景，先给最小可行方案，再说明何时需要扩展。

## 模块一 · 题 2：聊了 200 轮，如何压缩且保持流畅

我不会按“200 轮”触发，也不会简单保留最后 N 条消息。真正的约束是下一次请求的 token 预算：系统指令、工具 Schema、最近对话、工具结果、检索资料和预留输出都要计入。接近预算阈值时，按完整用户回合压缩，保留最近几轮原文，避免删掉未完成的 tool call/result 配对。

压缩内容分两层。第一层是确定状态，例如当前目标、任务进度、待办 ID、工具执行状态和产物地址，来自结构化存储，不依赖模型摘要。第二层是叙事摘要，保留决定、理由的简要说明、偏好、实体、时间和未解决问题。每条重要结论带来源事件 ID；不能把猜测压缩成事实，也不能反复“摘要的摘要”而完全丢失原文。当前用户输入和未闭合的工具链不压缩。

压缩后按“行为约束 → 结构化现状 → 标注为历史资料的摘要/召回片段 → 最近对话 → 当前请求”放置。用户说“刚才那个”时优先解析最近对话；问很早的具体数字时，从原始记录回查，摘要只负责找到线索。压缩在后台准备时必须绑定 history version；完成时版本过期，就只替换已覆盖的旧前缀，不能覆盖新消息。

验证不能只看省了多少 token。我会维护压缩前后的同题回放集：人名与数字、否定与更正、跨轮指代、未完成工具、用户改目标。比较答案正确性、工具误写率、追问澄清次数、成本和 P95 延迟。关键事实召回低于阈值就增加最近窗口或回查，不靠提示词要求“记得所有事情”。

本项目使用有界摘要＋最近完整回合＋待办数据库，摘要失败有明确降级提示。它未实现原文索引与来源回查，因此不承诺任意 200 轮细节无损保留。

## 模块二 · 题 1：半个月后用户重复提问，如何召回

“以前问过”不是直接把旧答案返回的充分条件。首先判断是想回顾旧结论，还是询问可能变化的新事实：用户偏好与过去决定可复用，天气、价格、进度等要刷新；旧答案本身也可能错。

召回在当前请求进入后、模型决策前触发。用当前问题加最近几轮做 query rewrite，补齐“那家公司”等指代；先按 user、访问权限、允许共享的 session/project 范围过滤，再做关键词＋语义混合检索。候选包括用户明确偏好、历史问答、关键决定和对应的来源事件；按相关度、时间、重要性与有效期排序，去重并限制 token。不要先全库搜索再让模型自己判断哪些内容属于当前用户。

写入时更克制：用户明确要求记住、反复稳定出现的偏好、已确认决定才形成长期条目，附来源、时间、置信度与有效范围；一次性闲聊留在会话记录中。更正和删除要能覆盖旧条目，不能让“你以前说过”压过现在的明确纠正。

例如用户问“我上次比较的两家工作机会，最后倾向哪家？”召回的是当时的候选、用户理由和日期，而不是一个孤立标签。回答可说“你在某日更倾向 A，理由是……”，并区分历史偏好与当前事实。若用户问同公司的最新薪资，只把旧范围作为背景，再查最新依据；没有最新来源就说明时间边界。

召回片段放在可标明来源的历史资料区域，不作为系统指令。低置信、实体冲突或时间失效时回查原文或澄清。验收使用跨天同义问、事实更正、无关问题不召回、跨用户隔离、删除后不召回等用例，重点看正确记忆命中率与错误召回率。

本项目中的待办只有几十项，每次按当前 user/session 精确查询即可，不需要向量库。半个月尺度的跨会话长期记忆属于后续能力，不能用当前的 session 摘要冒充。

## 模块三 · 题 1：长程任务如何避免忘记目标

单纯在 prompt 里重复“不要忘记目标”不足以维持任务。我会把任务契约持久化：目标、验收条件、约束、当前计划、已完成步骤、待解决问题、产物引用和预算。模型每轮只决定下一步，runtime 负责检查任务状态和预算，并在工具结果落盘后更新进度。

| 方案 | 适用与优点 | 代价或风险 |
| --- | --- | --- |
| 定期重新注入任务契约 | 最简单，可在每轮低成本校准 | 重复文字不能验证实际完成，也会占上下文 |
| 持久化计划＋检查点 | 跨压缩、崩溃后可恢复，能解释进度 | 计划会过时，必须允许根据证据重规划 |
| 阶段产物＋确定性校验 | 用测试、文件和业务状态证明完成 | 开放式写作难以完全自动验收 |
| 分阶段执行／隔离子任务 | 缩短局部上下文，适合独立任务 | 成本、交接丢失和目标不一致；不适合简单任务默认开启 |

我的默认组合是前三项。每阶段先写“完成的证据是什么”，执行后记录产物和检查结果，只有证据通过才前进；模型说 done 只是候选结束信号。若连续数轮产生同类错误、重复相同调用或没有新证据，runtime 暂停该路径，要求模型缩小问题、改计划或报告阻塞，不能无限循环。

用户改目标时新增 task version，明确哪些旧工作仍有效、哪些需要取消。晚到的旧版本工具结果可以归档为证据，但不能直接写入新计划或触发旧任务的写操作。恢复时先读取任务契约与最近检查点，再检查外部副作用，避免从头执行造成重复。

本项目只实现每回合循环上限、待办持久化与中断检查，没有实现长任务 scheduler 或自动验收引擎。若任务只有“查天气并记待办”，继续加任务树和多 Agent 会增加复杂度，没有收益。

## 模块四 · 题 2：busy 时新消息和异步完成事件如何处理

我会把 session 当作单写者 actor，外部消息先进入持久化 mailbox，由一个 worker 顺序改变会话状态。busy 只表示正在执行某个步骤，不表示拒绝一切事件，也不允许另一个线程直接修改同一份 prompt/history。

事件含 `event_id/session_id/sequence/task_version/type/payload`，先落库再回执。`event_id` 去重，sequence 定义 session 内处理顺序。用户普通追加消息进入队列，在当前模型调用或工具操作的安全边界合并处理；用户明确的取消／目标修正走控制事件，提升优先级并递增 task version。取消不等于回滚已经发生的外部副作用。

异步工具启动时创建 job，记录 call ID、关联 task version 和幂等键，返回“已受理＋job ID”。worker 等待外部结果时可以释放计算资源，并处理用户新请求。完成事件必须先更新 job，再投递 session；重复回调只更新一次。若当前 session 正在调用模型，先排队结果，避免半途改变已发出的上下文。

例子：V1 在导出报表时，用户要求改成 V2；稍后 V1 导出完成。系统保留 V1 产物并标为旧任务结果，可提示用户旧版已完成，但不把它当作 V2 的交付物。需要继续执行的结果在下一个决策点进入 context；不需要继续推理的结果可以直接形成状态通知，避免无意义模型调用。

数据库中 job 终态、会话事件和通知 outbox 同事务写入，后台投递通知并重试，通知消费也幂等。通知遵循用户订阅和 session 范围；不能让异步工具自行向任意联系人发送消息。长时间没有回调由 reconciliation job 查询外部任务状态，超时只是 unknown/failed 的候选，不能无依据宣布执行失败。

验收重点是竞态：新消息／完成／取消三个事件不同顺序，重复和乱序回调，worker 崩溃重启，以及通知发送成功但确认丢失。目标是副作用可去重、状态可解释、事件不丢，而不是笼统宣称 exactly-once。

本项目内置工具都是同步本地工具，采用更小的方案：同 session busy 立即返回错误，之后可重试；它没有实现上述持久化 mailbox 与异步 job。

## 模块五 · 题 1：Claude Code 与 GLM／豆包工具输出方式的差异

需要先区分层次：Claude Code 是 Agent 产品与 harness，GLM／豆包的 OpenAI-compatible function calling 是模型 API 能力。不能从“都输出一段 JSON”推导出运行时相同，也不能把某版本 CLI 的文本显示当作模型原始协议。以下比较底层通用协议，再讨论 harness；具体版本仍应以抓到的请求和官方文档为准。

| 维度 | Anthropic Messages 常见格式 | OpenAI-compatible Chat Completions 常见格式 |
| --- | --- | --- |
| 模型请求工具 | assistant content 数组中的 `tool_use`，含 `id/name/input` | assistant `tool_calls`，含 `id/function.name/function.arguments` |
| 参数表示 | `input` 通常是 JSON 对象 | `arguments` 是 JSON 编码字符串，runtime 还需解析并校验 |
| 工具返回 | user content 中的 `tool_result`，以 `tool_use_id` 关联，可标 `is_error` | `role=tool` 消息，以 `tool_call_id` 关联，content 常用序列化文本 |
| 多调用 | 一条 assistant 消息可以有多个工具块 | 一条 assistant 消息可以有多个 tool_calls |
| 富内容 | 内容块体系对文本和图片等统一表达 | 普通兼容实现多以文本为交集；多模态结果、reasoning 字段等需检查具体服务支持 |

内容块的优势是文本、工具调用和富内容可以在统一结构中表达；代价是适配时必须保留块类型、顺序和关联，不能 flatten 成字符串。OpenAI-compatible 的优势是客户端生态和迁移成本低；代价是“兼容”并不保证 strict Schema、并行调用、流式参数和多模态工具结果完全一致。GLM 或豆包具体模型是否支持某个能力，应基于模型与 endpoint 验证。

在 harness 层，真正影响使用体验的是大输出如何分页/截断/落盘，shell 任务是否后台化，权限如何检查，结果如何引用以及压缩后能否找回。无论底层用哪种协议，都可以由 runtime 实现这些能力；不能仅据协议断言 Claude Code 一定更强或兼容 API 一定不支持。

若适配两套协议，我会内部统一成 `ToolCall(id,name,args)` 与 `ToolResult(call_id,status,content,artifact_refs)`，边界 adapter 负责参数解析、块转换和供应商特有字段。保留原始关联 ID；超大输出存 artifact 并回传有界摘要和引用。对于流式调用，等完整参数和终止信号后才执行，不执行半段 JSON。

本项目只实现 Chat Completions adapter，不为假想的多供应商适配建立额外抽象。

参考：[OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling)、[GLM 工具调用](https://docs.bigmodel.cn/cn/guide/capabilities/function-calling)。Anthropic 格式可在 [Messages API](https://platform.claude.com/docs/en/api/messages/create) 核对；本次环境访问其文档失败，因此该部分依据公开协议结构写出，未声称验证当前 Claude Code 内部实现。
